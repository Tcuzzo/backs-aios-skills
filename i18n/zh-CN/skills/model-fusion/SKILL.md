# Model Fusion
**Effort:** heavy — 独立草稿、评审者以及可选的执笔者；仅当面板对任务的价值足以支持其在剩余预算内的开销时使用。

面板是可选的。不同执行实例为同一任务起草，未参与这些起草执行的评审者选择或
组合候选，再对照原始请求验证结果。同一个已配置且具备能力的模型可以在分开、
相互隔离的会话中承担起草、评审和执笔角色。不要求更换模型或服务商。
评审者不能继承作者的对话或工作上下文。

## 什么时候跑

- 当比较方案能解决明确的不确定性，而且评估工作符合任务剩余预算时。
- 当操作者明确要求面板时；说明可用角色和限制。任务规模大并不自动要求面板。
- 简单改动直接实现并进行适当验证。

绑定 [bounded-loops](../bounded-loops/SKILL.md)。起草、裁判、执笔和修复轮次
共用当前任务的截止时间、剩余尝试次数及资源额度。新增角色或会话不重置限制。
宿主支持时并行起草，否则在相同限制内依次执行。不要声称具备宿主未提供的会话隔离。

## 三个阶段

### 1. 面板 — 独立起草

1. 向每个隔离的起草会话提供同一任务和同一份任务上下文。
2. 每位起草者独立干活。谁也看不到别人的稿子。
3. 出错、超时或交白卷的起草者，记录在案后剔除。它绝不搞垮整轮。剔除要大声记录——绝不吞掉。
4. 收集所有非空候选。

### 2. 裁判 — 局外人来挑、来合

1. 评判之前，先对每个候选跑一道廉价的机械关卡：能干净地打上吗？能解析吗？探测跑在一次性副本上，绝不碰实况目录树。过不了关卡的候选，裁判连看都不看。
2. 两种裁判形态——按配置选一种：
   - **合成（Synthesis）：** 裁判分析每个候选（优点、缺陷、冲突），再由分开的执笔执行实例基于分析组合出最终答案。角色和会话保持分离；同一个已配置且具备能力的模型可以承担这两个角色。
   - **拣选（Selection）：** 裁判从过关的候选里挑出单个最优。更省。合并没增益时就用它。
3. 裁判或写手不可用时，就大声降级为对同一批候选做拣选。绝不悄悄浪费面板；绝不假装做过了合成。
4. 没有候选过关时，把最有价值的报错附到 prompt 上重跑面板——有界，最多 2 轮修复。用尽后返回失败并附完整错误清单。绝不把空结果或原样未动当成功返回。

### 3. 校验 — 拿赢家对照意图

1. 重读原始请求。赢家做到了要求的事吗——全部做到，而且没做没让它做的事？
2. 检查语义正确性、与周边代码的风格契合，以及它依然能干净地打上。
3. 信心不足就亮出升级旗，不许藏。然后按常规证明它：先失败测试，再变绿，再实况行为。一份从没跑过的合并稿只是猜测。

## 梯子

- 按所需能力、实际可用性、当前配置和剩余预算确定面板规模与角色。不固定模型、不预设服务商偏好，也不强制模型多样性。明确报告配置缺口。
- 配置格式、"代码里写角色、配置里放模型"、实况探测解析，都归 [fleet-ladder](../fleet-ladder/SKILL.md)。

## 硬性规则 — 破一条，技能即失败

- **构建者绝不当裁判。** 评审执行实例没有参与候选的起草，也未继承作者的对话或工作上下文。最终评分者必须使用全新且与作者上下文隔离的会话。
- **任何调用点都不许硬编码模型名。** 代码里是角色，配置里才是模型。
- **不许无声降级。** 起草者被剔、裁判回退、关卡失败、轮次用尽，全都要大声。评不了分的结果绝不默认通过。
- **修复有界。** 面板重跑有硬上限，并消耗当前任务的剩余预算；以最先触及的限制为准。额度用尽时给出明确检查点，绝不无限循环。
- **测试变绿不等于完事。** 赢家要在实况行为上得到证明。
